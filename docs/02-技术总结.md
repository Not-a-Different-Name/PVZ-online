## 1. 截图：这一个坑踩了整整一轮

> 这是本项目**最贵的一课**。我此前多次据截图断言「菜单是好的」，结论**全错**，
> 因为那些截图本身就是被拉伸过的假象。

### 1.1 事实（实测，非推断）

| 观测 | 结果 |
|---|---|
| 游戏进程自己建的窗口 | **DPI 感知**，客户区就是 **800×600 物理像素** |
| 干净启动、不做任何窗口干预 → 抓图 | `probe.png` = **800×600** ✅ |
| 经 `run_and_shot.ps1` 之后抓图 | `settle1to1.png` = **1002×752** ❌ |
| 经 `shot.ps1` 默认参数抓图 | `boards_reanim.png` = **816×639** ❌ |

`1002×752 ≈ 800×600 × 1.25` —— 本机显示器是 **125% 缩放，`dpi=120`**。

### 1.2 两个工具各自错在哪

**`tools/run_and_shot.ps1`**：它自己**没有**调用 `SetProcessDPIAware`，然后执行了

```powershell
[Win]::SetWindowPos($h, -1, 16, 16, 816, 639, 0x0040)
```

对一个 DPI 感知的游戏窗口，从未感知的 PowerShell 里发 816×639，Windows 按 1.25 解释
→ 窗口变成 **1020×799**，客户区 **1002×752**。游戏仍然只渲染 800×600，
DirectDraw 于是把 framebuffer **拉伸 1.25 倍**去填满客户区。

→ **它产出的每一张图（`boards_reanim.png`、`settle_w.png`、`settle1to1.png`）都是
拉伸过的，任何布局判断都不能用。** 这就是为什么 `boards_reanim.png` 看起来「被放大、
被裁切」——那不是游戏的问题，是我的截图工具的问题。

**`tools/shot.ps1`**：它做了 `SetProcessDPIAware`，也用 `-ClientW/-ClientH` 把客户区
强行掰回 800×600 —— 数字看起来对了，**但它是在掩盖一次不该发生的 resize**，而不是不去 resize。
更糟的是它用 `SetForegroundWindow` 抢前台，而 Windows 的**前台锁**会拒绝后台进程的请求，
于是 `CopyFromScreen` 悄悄抓到了**压在游戏上面的窗口**——实际抓到了我自己的终端。

### 1.3 正确做法：`tools/grab.ps1`（新写的）

三条规则：

1. **绝不移动、绝不缩放窗口。**
2. 用 `SetWindowPos(hwnd, HWND_TOPMOST, 0,0,0,0, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW)`
   把窗口**提到最前**——前台锁**不拦**这个，所以不需要抢焦点，也**不劫持桌面**。
   抓完再用 `HWND_NOTOPMOST` 恢复层级。
3. **必须打印客户区尺寸**，并且显式断言：

   ```
   dpi=120  client=800x600 at screen (17,46)  OK 1:1
   ```

   只要不是 `800x600`，这张图就**不能**用来判断布局。

另外：这个 build 的 stderr 里**没有** `[load-thread] COMPLETED` 标记
（旧脚本等的就是这个字符串，所以每次都白等满 90~120 秒）。`grab.ps1` 改成轮询
「窗口出现且客户区宽度 ≥ 400」作为就绪信号。

### 1.4 铁律

> **看不到 `client=800x600 OK 1:1` 的截图，一律视为无效证据。**
> 宁可重新抓，也不要据拉伸图下结论——过去所有「菜单是好的」错误结论都源于此。

## 2. DPI 虚拟化（已修，且**已复测确认**）

**症状**：窗口被系统当成 DPI 不感知，客户区变成 1000×750 物理像素，800×600 的
framebuffer 被上采样 1.25 倍 → 画面发虚、比例错。

**修复**：`main.cpp` 里在任何窗口创建**之前**、运行时绑定调用：

```cpp
typedef BOOL (WINAPI *SetProcessDPIAwareFn)();
if (HMODULE aUser32 = ::LoadLibraryA("user32.dll"))
    if (SetProcessDPIAwareFn aSetDpiAware = (SetProcessDPIAwareFn)::GetProcAddress(aUser32, "SetProcessDPIAware"))
        aSetDpiAware();
```

（之所以要 `GetProcAddress` 动态绑定：SDK 头把 `SetProcessDPIAware` 藏在 `WINVER >= 0x0600`
后面，而本项目仍按原版那个 Win98 时代的版本目标编译。）

**是否可靠**：游戏没有 `.rc` 里嵌的 manifest（`SexyAppFramework/LawnProject.rc` 只有光标资源），
exe 里也搜不到 `dpiAware` 字符串，所以 `SetProcessDPIAware()` 不会被 manifest 提前占用而失败。
**实测干净启动客户区 = 800×600，确认生效。**

> ⚠️ 之前记录里出现过 `client=1002x752`，与本条矛盾。按用户裁定
> 「**一切以最新状态为准，前后矛盾按后发生的为事实**」：那是 `run_and_shot.ps1`
> 自己 resize 出来的，**不是 DPI 回归**。

## 4. reanim 动画系统（`Sexy.TodLib/Reanimator.h`）

菜单几乎全部是动画画出来的，按钮控件只是透明命中盒。

| API | 用途 |
|---|---|
| `Reanimation::Update()` | 推进轨道 |
| `GetCurrentTransform(trackIndex, &t)` | 取某轨道当前变换 |
| `GetTrackInstanceByName` / `FindTrackIndex` | 按名字找轨道 |
| `AssignRenderGroupToTrack` / `AssignRenderGroupToPrefix` | 改渲染分组（`RENDER_GROUP_HIDDEN` 等） |
| `SetImageOverride` | 换图 |
| `PlayReanim` | 播一段动画 |

渲染分组：`DrawRenderGroup(g, 1)` 是 `"SelectorScreen_BG"`（背景层），
`RENDER_GROUP_NORMAL` 是正常层。所以**同屏物体的前后关系由渲染分组决定**，
不是由 `AddWidget` 顺序决定。

`trans=(-10000.0,-10000.0)` 是**哨兵值**，表示该轨道被要求隐藏/移出屏幕。

## 5. 全屏页面跳转范式（`LawnApp.cpp`）

框架里所有全屏页面都是 **`WidgetManager` 的顶层兄弟节点**，不是某个控件的子控件：

- `LawnApp::ShowGameSelector` (`:496-520`)：先移除并删除旧 selector，再 `new` 一个全新的，
  `AddWidget` + `BringToBack` + `SetFocus`
- `KillGameSelector` (`:524-532`)：移除 + `SafeDeleteWidget` + 置空
- `ShowAwardScreen` (`:536-544`) / `ShowCreditScreen` (`:560-567`)：
  `KillGameSelector()` → 新页面 `Resize(0,0,mWidth,mHeight)` → `AddWidget` →
  `BringToBack` → `SetFocus`

**成就页当初被挂成 `GameSelector` 的子控件，这就是它 z 序天然错乱的根因**
（`WidgetContainer::DrawAll` 按 `AddWidget` 顺序画，页面之上永远还有别的控件在画）。

## 6. 绘制路径（理解了才不会瞎猜 z-order）

- `WidgetManager::DrawScreen` (`WidgetManager.cpp:398-485`)：只画 `mDirty && mVisible`
  的顶层控件；**持久表面 `mImage` 从不清空**（唯一的清屏是 `PVZ_FULLREDRAW` 下的调试洋红填充）。
  这解释了为什么残留像素会「透」出来。
- `WidgetContainer::DrawAll` (`WidgetContainer.cpp:558-600`)：先画容器自己的 `Draw()`，
  再按 `mWidgets` 顺序画子控件；每个子控件拿到的是**按它自己 mX/mY 平移过**的 `Graphics`
  副本（平移从父到子逐级累积）；`mVisible` 是绘制开关，`mDirty` 只是被清掉、**不是**绘制开关。
- `Graphics::FillRect` (`Graphics.cpp:170-177`)：`mColor.mAlpha == 0` 直接返回；
  加 `mTransX/mTransY` 后与 `mClipRect` 求交；**`mColorizeImages` 不影响 FillRect**。
- `Widget::DeferOverlay` / `mDeferredOverlayWidgets` 是**死代码**，没人调用。
   `GameSelectorOverlay` 只是一个普通的最后加入的子控件，它的 `Draw` 里回调
   `mParent->DrawOverlay(g)`。

## 8. git：本项目最重要的一件事

**在建立 baseline 之前，整个项目没有可用的版本控制**，导致：

- 无法 `diff` 出「我改了什么」
- 无法回退
- 只能靠记忆，于是把代码一步步搅浑（`SelectorParkedX()` / `SelectorBGOffsetX()` 这层
  默认值为 0 的 env 脚手架就是这么留下来的）

**现状**（已修好）：

```
仓库：C:\Users\ThinkPad\pvz-online\re-plants-vs-zombies   ← 注意：仓库在子目录里，不在 pvz-online 根
分支：pvz-online（当前） / main
基线：11950d5  baseline: upstream c469203 + 本机已有改动（未验证，仅作起点）
上游：c469203  chore: more zombatar.
```

**核心工作流**：改一处 → `git diff` 自查 → 构建 → 截图 → 提交（提交信息写清
「改了什么 / 为什么 / 怎么验证的」）。详见 `规范.md`。

`.gitignore` 已忽略 `build-x86/` 与 `../runtime/`（后者是解包后的 PopCap 素材，
**绝不能入库、绝不能随 mod 分发**）。
