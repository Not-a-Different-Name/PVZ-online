## 一、问题是怎么发生的

### 1.1 起点：上游主菜单本来就是坏的

上游 `GameSelector` 的坐标设计**自相矛盾**，这是所有麻烦的源头：

| 位置 | 上游代码 | 含义 |
|---|---|---|
| `AddedToManager` | `this->Move(-800, 0);` | 整个 selector 控件的 mX 停在 **−800**（屏幕左侧外） |
| `GameSelector::Draw` | `g->Translate(800, 0);` … `g->Translate(-800, 0);` | **写死的 +800**，用来抵消 mX=−800，让 reanim 美术落在正确位置 |
| `GameSelector::DrawOverlay` | `g->Translate(-(mX + 800), 0);` | **用 mX 动态算**，只有 mX=−800 时才等于 0 |
| `TrackButton` | `mX = track.mTransX + offset` | 把按钮定位在**控件局部坐标**里 → 要正确显示就必须 mX=**0** |
| `mLoopCount > 0` 分支 | 把 `mBtnNoDraw` 全部置 false | 开场动画结束后才启用控件按钮，此前由 reanim 自己画按钮美术 |

**矛盾点**：美术要正确 → 需要 `mX = −800` 配 `Translate(+800)`；
按钮要正确 → 需要 `mX = 0`。**两者不可能同时成立。**

这就是上游那个「卡在 Click to Start 进不去菜单」的 bug 的物理原因：
`SlideTo(0,0)` 只在 `GameSelector_AchievementsBack`（注释标注 *seems to be unused*，
`:1370`）和 `ShowAchievementsWidget`（`:1497`）里被调用，**正常开局流程里根本没人把
selector 从 −800 滚回 0**，所以按钮永远停在屏幕外 800 像素处。

### 1.2 我的修改：把 −800/800 改成 0/0

我加了 `SelectorParkedX()` / `SelectorBGOffsetX()` 两个 env 脚手架，默认取 0：

```cpp
static int SelectorParkedX()   { ... EnvInt("PVZ_SELECTOR_X",   0); }
static int SelectorBGOffsetX() { ... EnvInt("PVZ_SELECTOR_BGDX", -SelectorParkedX()); }
```

- `Draw()`：`Translate(800,0)` → `Translate(SelectorBGOffsetX(), 0)`（默认 **0**）
- `AddedToManager()`：`Move(-800,0)` → `Move(SelectorParkedX(), 0)`（默认 **0**）

**对背景美术而言，两者是等价的**（`−800+800 = 0+0 = 0`），**所以这一步理论上不该
让背景错位** —— 但它确实破坏了 `DrawOverlay` 里那条基于 `mX` 的不对称补偿：

- 上游（mX=−800）：叶子 `Translate(-(mX+800))` = `0`，之后花朵 `Translate(mX+800)` = `0` → 对称 ✅
- 我的（mX=0）：叶子 = `−800`，花朵 = `+800` → **不对称，叶子和花各偏一边** ❌

**结论：这是我引入的一处真实回归**（影响叶片/花这类装饰，量级 800 px，必然肉眼可见）。

### 1.3 三个改动互相纠缠

`git diff` 最终钉住的是一组**三处同时改动**：

```diff
-	this->Move(-800, 0);
+	this->Move(SelectorParkedX(), 0);          // 停放 x: -800 → 0
-	g->Translate(800, 0);
+	g->Translate(SelectorBGOffsetX(), 0);      // 背景平移: 800 → 0
```
以及把 `mLoopCount > 0` 分支里上游的 `mBtnNoDraw = false` 改成了受 `PVZ_BOARDS` 控制。

**一次构建里塞了三处未验证的修改 → 截图无法归因。** 这正是 `规范.md` 要禁止的事。

## 三、已经确认的事实（有证据，可直接依赖）

### 3.1 主菜单几何（实测，非推断）

从 `PVZ_DUMP` 输出 + 从 `main.pak` 解包出的美术尺寸：

| 对象 | pak 内尺寸 | 屏幕坐标（实测） |
|---|---|---|
| `SelectorScreen_BG.jpg`（天空） | **100 × 75** | 小图块，由 reanim 缩放铺满 |
| `SelectorScreen_BG_Center.jpg` | 720 × 350 | `SelectorScreen_BG` 轨道 |
| `SelectorScreen_BG_Left.jpg` | 476 × 680 | 轨道 x **恒为 0.0**（稳定值） |
| `SelectorScreen_BG_Right.jpg`（**墓碑**） | 730 × 560 | 轨道 x **恒为 71.0**（稳定值） |
| `SelectorScreen_Adventure_button`（木牌） | — | 轨道 **x=405.0**, 宽 329 |

**铁证**：墓碑轨道 x=71 → 图片横跨 `71…801`；其**可见像素**（图片左上有大片透明）
大约从 x≈371 起、y≈99 起 —— **完全盖住 ADVENTURE 木牌所在的 `405…734, 108…233`**。

这**数字上精确复现了**用户的描述：
> 「adventure 木牌被 achievement 石头挡住，只能看到一半」

而且两份日志里 **X 完全稳定**（71.0 / 405.0），只有 Y 在动 → 说明**不是动画中间帧的问题，
X 就是 reanim 的静止姿态**。所以问题不在「采样时机」，而在**别处**（见 §4.1）。

### 3.2 其它确认项

- **`main.pak` 是活的**：`SexyAppBase.cpp:6118`；散装文件只是 `PakInterface::FOpen`
  (`:194-220`) 的回退。旧 `CLAUDE.md` 说它被注释掉是**错的**。
- **DPI 已修且已复测**：干净启动客户区 = **800×600**（`probe.png`）。
- **`mAchievementsButton` 挂在 `BG_Left` 上**（偏移 20,480），而墓碑美术属于 `BG_Right`
  —— 两者不同源，这本身就可疑。
- **成就页架构错误**：它是 `GameSelector` 的子控件，而框架内所有全屏页面
  （`AwardScreen` / `CreditScreen`）都是 `WidgetManager` 顶层兄弟节点。
- **`WidgetManager` 从不清空持久表面**（`WidgetManager.cpp:398-485`），
  这解释了残留像素「透」出来的现象。
- **上游 `PVZ_MARKER` 标尺**：以前加的洋红 100px 标尺可以用来快速目测比例。

### 4.4 堆断言（S4）：已定位并修复 —— 关窗时 `delete[]` 了字符串字面量

**结论（2026-10-02）**：本文此前的「当前构建不复现、按已被菜单修复覆盖结案」**是错的**。
真实症状：**手动关窗 → 调试堆断言（`_CrtIsValidHeapPointer` / `is_block_type_valid`）
→ 报告流程内 AV（ucrtbased.dll）→ SEHCatcher 弹 "Fatal Error!" 卡死**，
无联机的普通会话 100% 复现（`tools/close_repro.ps1` 三次运行三次命中）。
当时没复现出来的原因：那轮序列（成就页滑入/滑出、切档案）**没有走关闭程序这条路径**。

**根因链（符号化验证，非推测）**：
`LawnApp::Shutdown` → `TodParticleFreeDefinitions` → `DefinitionFreeMap`(DT_ARRAY) →
`DefinitionFreeArrayField` → `DefinitionFreeMap`(DT_STRING) → `delete[]`。
`Definition.cpp` 的 DT_STRING 释放条件写反（`if (*(char*)p == '\0') delete[] p`）：
**空串才删**——而空串全是字面量 `""`（`TodEmitterDefinition` 构造函数默认值；
缓存读取对零长串同样赋 `""`），真正由 `DefinitionAlloc`（`operator new[]`）分配的非空串反而泄漏。
`delete[]` 字面量不是堆块 → 调试堆断言。

**证据**：自写分配钩子（`_CrtSetAllocHook` + `_HOOK_FREE`）统计——一次完整运行
572,144 次 free **仅 1 次非法**，被释放指针 `0x01325601`（奇数，指向 exe 内 .rdata 的空串）。
两条方法论教训：
- `_CrtIsMemoryBlock` **不能**当校验器（对刚 `malloc`/`new` 的块也返回 false，
  已用进程内自检证实）；可信判据只有 `_CrtIsValidHeapPointer`。
- **SEHCatcher 打印的 "Logical Address" 比真实 RVA 小 0x1000**，符号化前要 +0x1000。

**修复**：`Definition.cpp` DT_STRING 分支改为「非空才 `delete[]`」（还原原版语义），
共享函数一次覆盖粒子/骨骼/拖尾全部定义表。验证：`tools/close_repro.ps1` →
非法释放计数 0、进程干净退出、`crash.txt` 不被重写。

**临时插桩**：本轮为定位加的 `PvzAllocHook` 等已于修复提交前摘除；
`PVZ_HEAPCHECK=late`（6a9517b）等其余插桩已在任务 #8 摘除（§4.3）。

#### 5.1.1 难度阶梯构想（2026-10-02 用户提出；**已在 M4-a 落地**，见 §5.7）

用户原话：

> 每五关僵尸血量增加20%，数量加20%；五关为一个难度阶梯，在同一场景，每关难度体现在
> 出现更强大的僵尸，每关僵尸数量增加；进入下一个场景，暂时不会出现更强大的僵尸，
> 因僵尸种类变化而难度略微回退，能够喘息。示例：一二关出普通 路障 （+铁桶僵尸）
> （+撑杆僵尸）3-5关渐渐出现读报，橄榄球，冰车，巨人僵尸等。除了泳池的部分僵尸
> 出现在特定场景外，其他大部分僵尸尽量不要限制出现场景。亟待讨论。

- 难度与场景**只由关卡号推出**：`mStartingLevel`/`mAllowedOnLevel[50]` 允许表 +
  `gZombieWaves[50]` 波数表；**没有独立的难度档位参数**。
- **没有僵尸血量的统一入口**：血量是每类僵尸在 `ZombieInitialize` 里的常数。
  "每五关 +20% 血量"需要**新增一层缩放**（可在初始化时对 `mBodyMaxHealth` 等乘系数）。
- **"数量 +20%"** 同样没有现成开关，需要自出波表或加一个数量乘数。
- **"不限场景"** 要放宽 `mAllowedOnLevel`，但**泳池/水域僵尸（必须有泳道）等硬约束
  必须保留**，不能一概放开。

### 5.5 联机同步：选卡等队友（SEEDS_READY）（2026-10-02 落地，待两机验收）

用户两机测试报："第三关后选植物开始时选好了不会等待其他人选好而是直接开始，造成不同步"。

**根因**：这道门**从未实现过**（全代码搜索无任何 online 门）——`SeedChooserScreen::OnStartButton`
→ `CloseSeedChooser()` → `mBoard->mCutScene->EndSeedChooser()` 直接放行，两边各按各的
Let's Rock 时间开打。前几关看不出来是因为卡池小、选项少（≤8 时甚至不进选卡界面）；
第三关后卡池大了，先选完的能领先一整段。修复：`MSG_SEEDS_READY = 15`（三字节
`{src, dst, u8 ready}`）+ `NetSession::SendSeedsReady/IsPeerSeedsReady`，`MOD_BUILD` 15 → 16。

**设计：两态状态，不是事件**（照 `LEVEL_DONE`/`PAUSE` 的成例）：

- 各家在**草坪建好**（`NewGame`）各报一次当下值：要选卡的报 0、这一关不用选卡的直接报 1；
  按下 Let's Rock 再报一次 1。收的人**只读不清位**——清位就是丢消息（对面报得早、
  本地清得晚，两边就互相干等）。新一轮的 0 会把上一轮的 1 盖掉，不会有残留提前放行。
- **报 0 必须报在草坪建好那一刻**，不能等选卡界面打开：欠三选一（含补发追赶）的机器
  可能过很久才轮到选卡，中间这段不能让对面以为"他早就选好了"（那会直接放行、白等一场）。
- **卡池 ≤8 的机器根本不进选卡界面**（`Board::ChooseSeedsOnCurrentLevel` 看**本机**卡池，
  两边可以不同）：它走不到 Let's Rock，必须由 `ShowSeedChooserScreen` 主动报"选好了"，
  不发就让人干等。这是设计里最容易漏的一个边界。
- 门挂在 `SeedChooserScreen::CloseSeedChooser` 第一行（拦下时身体一行没执行、卡槽未落定）；
  放行由 `LawnApp::UpdateOnlineSeeds` 每帧自检：对面也选好（或掉线）→ 撤等待框 → 重新走
  一遍关屏，重入时保留标记已清、重发被去重 → 直接通过。等待框 = "等待队友选卡"看板
  （复用 `DIALOG_ONLINE_START`；每帧自检再摆，被误关也不会把等待卡死）。

**设计期自查纠错（别重犯）**：第一版是"本机清位 + let-through 标志"，推演发现两个竞态——
(a) 本地在选卡界面打开时清对面状态位，会把对面"不用选卡直接报好"的消息擦掉 → 死锁；
(b) 上一轮的 stale true 会让需要补发追赶的机器新一轮直接放行。改两态后两个都消失，
还少两个状态位。

**验证**：MSVC 增量构建 EXIT=0（ninja no work to do = 与源码一致）；nettest 全绿
（新增 T25 两态往返：报 1 对面看得到、报 0 把 1 盖回来、同值重发去重、回主菜单/断线清表；
T26 三字节载荷严格、两字节按坏包断线）；改动文件 GBK 替换符检查 0。
实机待两机验收：**选完卡要等队友才开打**（第三关以后尤其明显，两边应同一刻开打）。

**R7 补丁（同日追加）**：卡池 ≤8 的关卡全程不开选卡界面、按不了 Let's Rock——上面那道门
它**根本走不到**，`ShowSeedChooserScreen` 报过"选好了"之后还是一个人先开打（不同步在这里
换了个形状又冒出来）。补法：把门复制到 `LawnApp::UpdateRunPick` 的"picks done"段
（报过状态之后、`StartLevelIntro` 之前）：卡池≤8 + 联机 + 有队友 + 有人没报好就拦下——
`mOnlineSeedsHeld` 挂起、等待框照摆，**草坪保持冻结**（`mRunIntroHeld` 留 true，
`CutScene::Update` 一步不走）；拦下期间 `UpdateRunPick` 顶部对该标记早退（选卡界面已建过，
重入会撞断言）。放行仍在 `UpdateOnlineSeeds` 收口，按 `ChooseSeedsOnCurrentLevel` 分流：
卡池>8 → 重走关屏（`CloseSeedChooser`）；卡池≤8 → 解冻 + `StartLevelIntro`。

### 5.6 闯关开局不再演戴夫问候（2026-10-02 修复）

- **现象（用户实机）**：局域网开局时戴夫出来讲话（"那些僵尸一直来"云云）。

### 5.15 闯关僵尸种类丰富化（2026-10-03 落地，待实机验收）

用户指令：「试玩后发现僵尸种类主要还是普僵路障。我希望丰富僵尸种类，让眼花缭乱的僵尸
都出现。**不要减少僵尸数量**，高压能带来游戏乐趣和成就感。不同顺位僵尸数量和点数随
顺位乘数增加」。

**根因（三叠加）**：① 原版 `gZombieDefs` 的 `mPickWeight` 极端偏斜——普僵 4000 /
路障 4000 / 铁门 3500，其余全是 1000-2000。按权重抽，半个战场都是普僵+路障（实机感受
的来源）；② 场景 1 名单原本只有普/路障/撑杆三样，开局两种小关里翻来覆去就这几张脸；
③ 闯关点数曲线早期极低（`aWave*2/5+1`），前几波只买得起最便宜的类型，强怪连抽的资格
都没有。

- **修法一：权重平铺（`RunZombieWeight`，RunZombieRoster.h/.cpp）**。闯关分支里用
  "平铺"权重替代原版权重：名单内类型一律同权（`RUN_ZOMBIE_PICK_WEIGHT`=1000）。
  种类分布立刻散开；强怪的出现频率不靠权重压制，交给"买得起"闸（点数）与每波
  巨人上限（`RUN_GARGANTUAR_CAP`）管。**权重为 0 的特殊类型（鸭子圈/旗帜/伴舞——
  它们不走随机抽取这条通道）保持 0**，不开新口子。只在闯关分支生效，非闯关局与
  原版一字不动（Board.cpp `PickZombieType` 的 `IsRunMode()` 分支）。
- **修法二：名单提速"v2"（RunZombieRoster.cpp 表）**。整表相对 M4-a 版提前 1-3 个子关：
  白天 sub1 就四样（+读报）、sub2 +铁桶/铁门、sub3 +橄榄球/气球、sub4 +跳舞/冰车、
  sub5 +矿工/跳跳；夜里 sub2 上普通巨人、sub3 红眼、sub4 小丑盒、sub5 蹦极；泳池五关
  依次 +鸭子圈/潜水/海豚/雪橇/梯子；雾 sub2 +投石车。屋顶五关维持 M4-a 的 18 种定表
  （潜水/海豚/冰车/雪橇剔除——行约束本就刷不出/观感不对）。行/场硬约束照旧自动兜底。
- **修法三：点数曲线抬脚（Board.cpp `PickZombieWaves`）**。闯关分支
  `aZombiePoints = aWave*2/5 + 3`（原 +1）——起步 +2 点/波，让前几波就买得起中档怪，
  总只数只会更多、不会更少。**没有动任何"减数量"的旋钮**，反而把总点数抬高了。
- **顺位乘数**（§5.13）本就把数量与点数一起放大（`aZombiePoints *= aSeatMult`、
  每波上限 `RUN_WAVE_ZOMBIE_CAP × aSeatMult`），满足"不同顺位僵尸数量和点数随顺位
  乘数增加"，本次一字未动。
- **MOD_BUILD 24 → 25**：协议一个字没动，但波表由种子两端各算——公式不同（权重表与
  点数曲线都变了）时同一关两边算出的怪种与数量都对不上，必须两边同版本。
- 验收要点：闯关局里普僵/路障不再是绝对主体，各类型"眼花缭乱"轮流出现；同一关
  僵尸总数 ≥ 旧版（不降反升）；四人局 1 号位依旧最多、4 号位与单机同关数量一致；
  两边同版本联机，同一关两边观感一致（波表同源）。

### 5.19 末位推车：末位玩家每行一台、整局一次性（2026-10-03 落地，待实机验收）

  屋顶关发屋顶清洁车型）。单机闯关照旧没车。
- **一次性记账**：消耗点 = `LawnMower::StartMower`（触发，TRIGGERED 早退防重复）与
  `SquishMower`（被压扁），各调 `Board::NoteMowerConsumed(row)` → `RunState::mMowerUsedRows`
  （bit = 行号）。只在**联机闯关**记账：联机原版战役的车每关重置（不记），单机没车。

  按"一辆都没用"续）。**协议零改动、MOD_BUILD 27 不动**——纯本地机制，联机两端各记各的。
