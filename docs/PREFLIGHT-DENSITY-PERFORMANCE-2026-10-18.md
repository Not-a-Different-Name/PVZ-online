# 高密度场面预防排查与对象池处理方案（2026-10-18）

## 结论与范围

玩家反馈：多人联机中单个客户端闪退，较多出现在 P1 和僵尸较多时，少数无明显征兆；尚未取得玩家实际闪退日志，不能把全部闪退归因于一个问题。

已确认并修复两类问题：之前的成组僵尸生成容量检查及生成失败处理；本轮发现的固定 2048 项绘制列表越界。当前 PC / Android 源码均包含修复，双端原生编译通过。源代码已合入本地并行进行的 Build72 足球 Boss 改动，因此本轮最终构建版本为 Build72。原有 Build71 文件名是排查批次编号。

动画、子弹、掉落物与附件池耗尽仍存在其他风险，尚未全面修复。以下方案中标为“建议”的内容没有实施。没有降低刷怪倍率、删除场上僵尸或改变伤害来规避这些问题。

## 已修复并验证

原绘制列表固定 2048 项，僵尸及子弹通常各占两项（主体、阴影），另有植物、界面等项。真实引擎构建结果：

| 僵尸 / 子弹 / 植物 | 绘制项 | 原上限 | 新缓冲区容量 |
| --- | ---: | ---: | ---: |
| 100 / 100 / 30 | 436 | 2048 | 972 |
| 300 / 300 / 30 | 1236 | 2048 | 2572 |
| 600 / 600 / 30 | 2436 | 2048 | 4972 |
| 850 / 850 / 30 | 3436 | 2048 | 6972 |

新实现按各类当前池内对象数量计算保守上界，给植物、Boss、蹦极、格子等多绘制项对象留足空间，保持原绘制顺序。缓冲区按本次调用拥有，避免重入绘制共用缓冲区。未改变 Board 数据字段及存档布局。

验证：6 组场景均通过绘制列表容量及尾部哨兵检查，空缓冲区、容量不足缓冲区均被拒绝；600 / 600 场景实际执行完整 DrawGameObjects，通过。此前僵尸容量边界的 17 项回归检查全部通过。

源代码：两端 Board.cpp 的 GetRenderListCapacity、BuildRenderList、DrawGameObjects；Board.h 增加方法声明。

## 未修复风险及建议

| 优先级 | 风险 | 处理建议 |
| --- | --- | --- |
| P0 | 动画池 1024，普通僵尸身体、旗帜附件、植物、掉落物等共享；满池分配主要依赖发布版不起作用的断言 | 增大经过测量的初始容量；创建一整组实体前预留其必需动画；仅装饰动画可降级；逐个检查调用方 |
| P0 | 子弹池 1024，AddProjectile 与多处调用方未处理容量失败 | 增加容量、运行时边界检查与调用方检查；优先保留战斗子弹；任何延迟发射政策都需明确其节奏影响 |
| P0 | 金币 / 阳光等池 1024，部分调用方立即解引用新对象 | 增加容量；按类型审查合并或待生成队列，保留价值、归属、位置和寿命语义；种子包和特殊奖励单独处理 |
| P0 | 附件池 1024，且单个附件最多 16 个效果；部分分配仍仅有断言 | 同时保护总池和单个附件数组；装饰效果降级；必需效果预留，不能只扩大总池 |
| P1 | 存档读取未完整校验 maxUsedCount / size / freeHead；Android 部分长度字段在验证剩余数据前用于分配 | 先验证计数、大小、乘法溢出和数据剩余长度；坏档退出读取并保留原文件；区别于正常战斗路径 |
| P1 | 子弹碰撞、部分寻敌与范围伤害遍历全部僵尸 | 按行 / 空间分桶；覆盖跨行、Boss、魅惑、特殊攻击与目标顺序，不能改变伤害结果 |
| P1 | 网络主线程同步发送，失败重试可长时间占用；接收队列有容量上限 | 单独处理发送阻塞、背压和队列，更多是卡顿 / 断线风险，尚无证据证明为此次闪退原因 |

动画池先耗尽的示例：30 株需要双动画的豌豆植物占 60 个动画，500 只需要身体和旗帜的旗帜僵尸占 1000 个，总计 1060 个，尚未计入其他界面和特效。僵尸池此时只有 500 个实体，不能仅按僵尸数判断安全。

僵尸池满时建议保留待生成请求，组合单位整体预留空间，空位释放后继续生成，并避免把“等待生成”判为该波已结束。队列同样需要容量与处理速率约束：持续生成速率大于回收速率时，任何有限队列最终都会满。排队会改变出场时间，需要验证波次重叠、计时与难度；不能声称与原节奏完全一致。

不得对现有连续 DataArray 简单执行扩容搬迁：引擎保留对象裸指针，搬迁后可能产生悬空引用。较低风险的第一阶段是在开局分配足够容量；真正动态扩容需要稳定地址的分块存储，并重做遍历、ID 定位、释放、保存 / 读取等接口。

DataArrayGet 目前有 `(short)theId` 的索引转换，ID 本身也有位宽约束。子弹的 mRunWaveHitIds 固定为 1024 项。提高僵尸容量前必须审查这些固定数组的使用方式、去重语义与存档兼容性，不能只改初始化数字。

## 性能计算

测试机器：AMD Ryzen 9 7945HX，16 核 32 线程，约 31.22 GiB 物理内存。PC x86 Release 引擎代码，独立测试档案，普通僵尸、30 株植物、维持固定数量的普通子弹。每组预热 30 次，测量 300 次更新。为维持碰撞负载，每次测量前恢复子弹位置，该准备工作不计入更新耗时。

| 僵尸 / 子弹 | 逻辑更新中位数 ms | P95 ms | P99 ms | 额外绘制列表构建排序中位数 ms |
| --- | ---: | ---: | ---: | ---: |
| 100 / 100 | 0.159 | 0.258 | 0.294 | 0.017 |
| 300 / 300 | 0.962 | 1.484 | 1.904 | 0.061 |
| 600 / 600 | 3.298 | 5.008 | 5.896 | 0.178 |
| 850 / 850 | 5.972 | 8.518 | 10.128 | 0.267 |
| 600 / 100 | 0.869 | 1.914 | 2.792 | 0.071 |
| 100 / 600 | 0.573 | 0.753 | 1.056 | 0.060 |

标准逻辑步长 10 ms，即每秒 100 次。850 / 850 的中位数占单步预算 59.7%，P99 占 101.3%，尚未包含完整绘制、声音、网络等成本。不能将这些数据换算成实际 FPS 或安卓成绩。

普通子弹碰撞查询每次扫描全部僵尸，理论候选遍历量约为 Q × Z × 100 / 秒：

- 600 × 600 × 100 = 3600 万次候选遍历 / 秒。
- 850 × 850 × 100 = 7225 万次候选遍历 / 秒。
- 1024 × 1024 × 100 = 1.048576 亿次候选遍历 / 秒。

这是候选遍历次数，并非 CPU 指令数或实际命中判定数；行过滤、早退等会影响实际成本。把僵尸和子弹上限同时翻倍，碰撞最坏扫描量约为 4 倍，不能用“还有内存”推断性能足够。

600 / 600 场景单次离屏软件绘制用时 65.665 ms，仅验证完整绘制路径和展示该特定软件路径成本，不代表实际显示性能。单独计时的查询、快照和绘制准备不是完整游戏帧；其中碰撞本已包含在逻辑更新内，不能重复相加。

## 内存计算

PC 实测 sizeof：Zombie 380、Plant 380、Projectile 4336、Coin 216、Reanimation 156、Attachment 776 字节。DataArray 每槽还存放 4 字节 ID。

- 子弹池 1024 槽：4340 × 1024 = 4,444,160 字节，约 4.24 MiB。
- 子弹池若改 4096 槽，仅槽数组额外约 12.71 MiB；不能据此直接选定 4096，还需性能与存档测试。
- 每颗子弹的 1024 项命中记录占 4096 字节，约为结构大小的 94.5%。后续可以研究稀疏记录，但必须保留重复命中规则。
- 动画池若从 1024 改 4096，槽结构本身增加 160 × 3072 = 491,520 字节，约 0.47 MiB；动画轨道等动态分配另外计算，因此这不是动画扩容总成本。
- 测试进程私有内存约 376.7–383.1 MiB，工作集约 419.1–429.3 MiB，包含资源与引擎；不能作为安卓内存数据。系统内存富余不等于固定池不会越界。

## 为什么 P1 更明显

在线席位倍率按实际占位顺序计算：6 人为 32、16、8、4、2、2；3 人为 4、2、2。关底 Boss 固定出现在 P1。P1 因此更容易遇到高对象数，并非已证明“房主统一模拟所有客户端”。单波列表容量与场上实体池容量不同，波次重叠及组合召唤也会增加瞬时需求。

## 建议实施顺序与验收

1. 首先补齐各分配边界和所有调用方的失败处理。必需对象按组合预留，装饰对象允许受控降级；记录池名、容量、高水位和失败来源，日志限频。
2. 开局预分配更合适的动画、附件和子弹容量，容量值依据双端压力测试确定；保留存档升级及读取校验。
3. 实现必要生成请求的有限队列和波次等待状态；装饰特效做优先级回收。队列积压需要可观测，不能无界增长。
4. 按行 / 空间优化碰撞查询，验证伤害与顺序一致后，再考虑进一步放大支持规模。
5. 只有仍有实际需要时再迁移为地址稳定的分块池，作为独立重构验收。

验收需覆盖：上限前一项、恰好满池、超过一项、反复释放重用、组合生成、Boss 召唤、跨波积压、读写旧档、Android 内存压力。除“不崩溃”外，还应检查怪物与奖励总量、命中次数、目标优先级、波次结束与队列耗尽。持续生成大于回收的情况要单独验证。
