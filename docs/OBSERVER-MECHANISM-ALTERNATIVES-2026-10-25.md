## 一、现状

### 1.1 产品里同时存在两套观战

| | 简图观战（v1，legacy） | 完整画面观战（v2，observer-normal1） |
|---|---|---|
| 协议 | 消息 17/18（type 18 简图快照 ≤256B，可走 0xF011 flow 包裹） | 消息 30（控制）/31（帧），`ObserverWireV2` SCHEMA=2 |
| 界面 | `Lawn/BoardWatch.cpp`：图标+血量数字+「换人」按钮的简板（移动端风格） | 本机正常绘制资源重放的完整草坪 + 顶部「正在观看 P{n} · 延迟约1.5秒」横幅 |
| 刷新 | 源端每 7 个 update 周期向订阅者发一帧简图 | 源端每 500–2000ms 自适应采一帧完整显示 DTO |
| 拥挤时 | **唯一可被丢弃**的观战流量（`legacyObserverSnapshot`）；客户端接收预算 224/256 槽 | 不可丢弃；拥堵时暂停采集/回 BUSY，不挤占战斗 |
| 状态 | MOD31 起的历史功能，保留兼容 | MOD94 正式交付、MOD95 修图集排序；重连等待席可看不可被看 |

### 1.2 v2 完整链路（已上线基线）

**协议常量**（`Lawn/Online/ObserverWireV2.h`）：
- 控制（30）：BEGIN/ACCEPT/KEEPALIVE/STOP/UNSUPPORTED/BUSY；字段 watchId、boardStream（源代次）、roundEpoch、features（revision 0x9402）、budgetKbps（24576，**固定协议常数**，双端一致才收）、playDelayMs（1500，限 1000–2000）。
- 帧（31）：40B 头 = src/dst + watchId/stream/frameSeq/sourceTick/roundEpoch + partIndex/partCount + encoded/raw/CRC32；每片负载 ≤216B、**≤304 片**；单帧编码后 ≤64KB、原始 ≤128KB。flow 开启时走战斗 flow 包裹（term/epoch），复用战斗通道但独立队列。

**源端（被看的人）**（`Lawn/Observer/ObserverBoard.h` + `ObserverDrawScene.cpp`）：
- 在**正常 BuildRenderList 绘制边界**用 `DrawRecorder`（一个画布型 Image，不建第二个 Board、不发指针/轨道地址）采集纯显示 DTO：绘制命令（≤8192 条）+ 资产键（kind/id/item/filters → 本机资源编号）+ 运动参数（Motion：kind 1–3、vx/vy/ay/life）+ 标志（暂停/出奖/推演位）+ 波次 wave/total。
- 采集间隔自适应：`(采集+编码耗时)×100` 钳在 500–2000ms——源端机器越弱帧距越大。
- 只发给已 ACCEPT 的观看者；采集/编码失败即暂停并回 BUSY。网络侧走 `NetLink` 独立有界观察队列，战斗优先。

**中继（Go，`server/relay/observer_v2.go` 等）**：
- 能力协商 0xF023：客户端每 2s 查询，服务器回 revision+24576；build<94 不认。
- 订阅鉴权：同房、双方席位在线、双向能力、term/epoch 与当前局一致；KEEPALIVE 4s 续约，超时/换局即清装配。等待席（roundWaitMask）**只能看不能被看**。
- 每观看席位一个订阅槽 + 有界装配；输出队列 8MB 上限、最新帧优先替换。
- **全局预算**：每秒观战字节 = `SendBudgetMbps×20%`（运营配置），未配置时缺省 256KB/s（≈2.1Mbps）；超了直接拒，另有 `observerBusy` 全停开关。
- 中继**不渲染、不存棋盘状态**，只校验结构/序号/归属后扇出——延续「棋盘主权在客户端、服务器无状态 1G 小机」的既定架构。

**观战端**：
- BEGIN→ACCEPT（45s 收不到首帧即超时提示「画面暂不可用，请换一位队友」）；装配拒乱序/过期；完整帧进 2 帧收件箱。
- `Timeline`：1500ms 播放缓冲（≤12 帧/8MB），3s 无流量自动关，源节奏漂移 >2s 拒收；`DrawScene` 用本机可信图集/动画定义重放，MOD95 同尺寸图集稳定排序后复杂草坪**像素差 0**。
- 兼容门槛：对端 build<95 直接拒收（双端都要 MOD95+）。

### 1.3 正在实施的单次快照本地观战（`work/observer-local-20261025/`）

已确认范围（AGENTS.md，2026-10-25）：
- **一次请求**：看一眼 = 一次快照；收到后**本地只读推演到退出**。
- 推演边界：只推进**已有对象**的移动（Motion）与动画（新增 `VisualAnimation/VisualTrack` 动画态采集，钩子在 `Reanimator.cpp` 绘制路径 + `Board.cpp` RenderItem）；**血量/阳光冻结在采样值；不推算生成、伤害、死亡、胜负**。
- 全局限额沿用/收紧中继预算；**5 秒请求冷却、合计 0.2Mbps 两个具体数值的建议仍待用户答复**，实现按可调参数准备。
- 已备份 20 个文件（双端 10 文件 + server/relay 全目录）见 `BEFORE.json`；后续按固定来源完整双端交付+回归。

## 二、问题（现机制的真实成本与短板）

1. **带宽按「观看者 × 房」放大**：单帧编码后上限 64KB（最坏 304 片突发），0.5s 间隔下单个订阅**理论上限 ≈1Mbps**；实际帧小得多，但中继全局预算一紧就拒/BUSY，观战可用性与并发观众数直接互斥。
2. **1.5s 固定缓冲**：为平滑 304 片突发而设；跨网弱链路时观战体感延迟明显高于操作者。
3. **源端弱机自适应降到 2s/帧**：弱机当源时观战变幻灯片。
4. **冻结类信息（血量/阳光/波数）只能靠整帧刷新**：帧距 = 信息延迟。
5. **双协议双 UI 并存**：v1 简图与 v2 完整画面两套 wire、两套界面长期同维护。
6. **验证债**：安卓真机/混合跨网未实测；任何再动协议的方案都会继承这笔债。
7. **出口是云服务器唯一计费资源**：观战全部流量都过中继（1G 内存小机），观战规模上限=出口带宽上限（当前全机 ~4.1Mbps）。

## 三、可行替代方案（方向清单，不拍板）

| # | 方向 | 一句话 | 相对现制的增益 | 主要代价/前提 |
|---|---|---|---|---|
| A | **定期关键帧 + 本地推演** | 把「一次请求」参数化成「每 N 秒/冷却后可再拍」 | 带宽从连续流降到 1/N，血量/阳光过期有界 | wire 不用改（flags 已有推演位）；需要定 N 与冷却策略 |
| B | **事件触发补帧** | 源端在波次推进、暂停恢复等离散时点主动补一帧 | 花小带宽保关键信息；wave/total/paused 已在帧头 | 需定义「值得补帧」的事件清单；源端多一处策略 |
| C | **帧间差分编码** | 命令列表已经是结构化 DTO，帧间只发 diff/脏区 | 同带宽下帧率×数倍，或同帧率带宽÷数倍 | codec 双端同构改造+新旧版本门槛；装配端要缓存基帧 |
| D | **语义状态同步（实体级协议）** | 发实体状态（僵尸 id/行/坐标/血量、植物格、阳光、波次），观战端重建画面 | 每保真度带宽最低、中途加入最便宜 | 要在**渲染边界之外**新开状态导出面（现安全设计刻意避开）；每加新实体都要扩协议；v1 简图即此思路的低配版 |
| E | **观战端事件重放 + 只读模拟** | 订阅战斗事件流，观战端跑只读 Board | 画面最"真" | 与本批冻结规则直接冲突（生成/伤害不可推算，需种子/检查点同步）；等于推翻「严禁第二个 Board」红线 |
| F | **中继录制/检查点回放** | 源端传检查点，中继存储，观战端下载推演 | 观战与源端解耦、可做延时复盘 | 中继从无状态变有状态（1G 内存机）；检查点大；新存储面 |
| G | **P2P 直连观战** | 观战流量不过中继，观战端直连源端 | 中继出口归零（局域网场景） | 局域网 DIRECT 通道已具备；公网受 NAT/打洞限制，官方服玩法全是 relay，等于只覆盖自建入口 |
| H | **分级观战** | 等待席/弱网默认简图或画中画小窗，完整画面按需升级 | 出口预算按需分配；两套 UI 正好是现成的两级 | 需要定级差规则与切换入口；小窗合成（多源同屏）是新绘制工作 |
| I | **公平队列 / 每观看者令牌桶** | 全局预算一刀切+observerBusy 全停 → 每订阅配额+排队 | 高峰不再「全有或全无」 | 中继策略改造；配额数值要定；先到先得 vs 轮转要选 |
| J | **观战端本地录制回放** | Timeline 帧流落盘，观战者本地复盘 | 零服务器改动、零新增带宽 | 仅观战端可见；磁盘与隐私口径需确认 |

> A、B 是本批「单次快照」的自然延伸（同一 wire、同一冻结边界内调策略）；C 是传输层优化；D/E/F 动架构；G/H/I/J 是部署/产品形态选择。

## 四、风险

- **A/B**：本地推演的诚实性风险——血量/阳光冻结、新僵尸不出现，观战画面与真实局偏差随时间拉大；补帧节奏与信息时效的平衡要实测（这正是待答的冷却/0.2Mbps 数值问题）。
- **C**：差分基帧丢失/换源/换局时的重建正确性；新旧客户端互通门槛再次抬高（现已 build≥95）。
- **D**：状态导出绕开渲染边界后，等于新开一条「读棋盘内部状态」的通道——隐私/作弊面、维护面（每种新实体/新 buff 都要进协议）、跨版本兼容三头都要管。
- **E**：违反已冻结红线（不建第二个 Board、不推算生成/伤害）；确定性同步在跨端（PC/安卓）上的随机流一致性没有现成基础。
- **F**：中继有状态化与「无状态 1G 小机」运维现实冲突；磁盘/内存上限即观战上限。
- **G**：公网 NAT 下基本不可用；若只做局域网入口，与官方服自动选服的既定玩家口径不冲突但覆盖面小。
- **H/I**：分级/配额规则本身成为新争议点（谁看得到完整画面、挤掉谁）。
- **通用**：所有方案都要过「六席五观众+真实重连等待席」这套已验收回归；安卓真机/混合跨网长局这笔债不因换方案消失。

## 五、矛盾（需要用户收敛的取舍）

1. **完整画面 ↔ 出口带宽 ↔ 实时性**三角：三者现各占一头（全帧=带宽贵，1500ms 缓冲=延迟，单次快照=信息冻结），没有同时改善的免费午餐。
2. **本批方向 vs 已上线机制的关系**：单次快照落地后，MOD95 的周期流是**替换、并存还是参数化成同一机制的两个档位**——协议兼容，纯策略问题，但影响中继预算怎么配。
3. **无状态中继 ↔ 更强观战**：录制/回放/服务器合成都要求中继有状态，与既定架构和 1G 内存机冲突。
4. **渲染边界安全设计 ↔ 语义协议的便宜**：D 方向省带宽，但放弃「只发显示 DTO、不发棋盘状态」这条刻意选的安全边界。
5. **兼容门槛 ↔ 升级节奏**：现制要求双端 MOD95+；玩家群升级不同步时，低版本玩家既看不了也当不了源。
6. **交付纪律 ↔ 参数调优**：每批都要固定来源完整双端包+全量回归，而观战手感（缓冲、帧距、冷却）天然需要快速迭代小调。

## 六、创新点（未定案，仅记录）

- **等待席战况条**：只用帧头 wave/total + 标志位发文字进度（「第 3/10 波 · 队友暂停」），近零带宽，适合重连等待席默认展示。
- **画中画小窗**：以 v1 简图做多席位小窗拼屏、点开任一席升 v2 完整画面——两套现成机制组合成「矩阵+特写」。
- **推演到期标注**：冻结值画面上加「快照已 N 秒」角标，把信息陈旧从误导变成明示（纯观战端 UI）。
- **观战一键互动**：复用现有快捷消息/表情通道做「喝彩/求援」，零新增协议。
- **本地复盘**：J 方向延伸——观战过的局可在结束界面回放，形成轻量「录像」功能。

## 七、当前待用户定案的问题（实现已按可调参数准备，数值未锁）

1. 单次快照的**请求冷却**（建议 5 秒）与观战**合计带宽上限**（建议 0.2Mbps）是否按建议值定案。
2. 补帧策略走 A（定时）还是 B（事件触发）还是两者组合。
3. 单次快照批上线后，与既有周期流的关系（替换/并存/档位化）。
4. 等待席默认观战档位（简图/战况条/完整画面）。

## 八、量化测算：2核2G 3M 小服务器、300 人、50 观战（2026-10-25 追加）

> 口径：3M 带宽 = 3 Mbps = 375 KB/s 出口；观战流量全部过中继。标注「估」的数字未实测，其余由 2026-10-25 采样与源码常量推出。

### 8.1 底账（先于一切方案的前提）

| 项 | 数值 | 来源 |
|---|---|---|
| 每玩家基础中继出口 | **≈14–15.5 kbps（1.8–1.9 KB/s）** | 实测 1.887M/133 人、2.206M/142 人 |
| 300 人基础流量（单机） | **≈4.4–4.6 Mbps > 3M** | 上行 ×300，线性外推 |
| 现网形态（2 台） | 每台 ~150 人 ≈ 2.2M，**余 ~0.8M/台** | 实测 + 3M 管道 |
| 观战预算/台 | 0.8M ≈ 100 KB/s；25 观战/台 → **每人 4 KB/s**；50 观战挤一台 → 每人 2 KB/s | 减法 |
| CPU/内存 | 2C 够（现网 CPU/内存余量足）；**内存须下调 observerMemoryLimit（现 8MB/人，50 人最坏 400MB → 建议 ≤1MB）** | 源码常量 + 采样 |
| 必改运营参数 | `SendBudgetMbps` 未配置时观战缺省帽 = 256KB/s ≈ **2.1M，会把余量一口吃光**，3M 机必须显式设小；`observerBusy` 全停做保险 | observer_v2.go + operations_config.go |

**结论 0（门槛事实）：300 人放单台 3M 机，观战为 0 时基础对局流量就已经超管道（~4.5M > 3M）。** 300 人 = 两台机（每台 ~150 人）才成立；每玩家出口降到 ≤10kbps 才可能单机装下且毫无观战余量。以下全部按「两台 × ~150 人 × 各 ~25 观战」测算，并给出单机 50 观战的坏情况对照。

### 8.2 各方案 50 观战出口测算与判定

| 方案 | 单人持续开销 | 50 人合计 | 判定（余 0.8M/台） |
|---|---|---|---|
| 现行 v2 连续流（对照） | 帧尺寸×帧率：4KB×1fps=4KB/s；10KB=10KB/s（帧尺寸**未实测**，上限 64KB） | 0.8M @4KB、2M @10KB、4M+ @20KB | **大概率不够**：仅当典型帧 ≤4KB 才撑 ~50 人（25/台），忙草坪多半超；现实支撑 ~10–20 人 |
| 单次快照，仅 5s 冷却、无合计帽 | 10KB/5s=2KB/s；16KB 快照=3.2KB/s | 0.8M @10KB；1.28M @16KB **超** | 冷却挡不住总量（50 人最坏同时拍），**必须叠加合计帽** |
| 单次快照 + 0.2M 合计帽 | 0.2M=25KB/s → 每人 0.5KB/s = 10KB 快照/人/20s | ≤0.2M | **够**，体验=「看一眼、隔几十秒可再拍」（待答的两个数值在此约束下的真实含义） |
| A 定期补帧 20–30s + 本地推演 | 10KB/25s=0.4KB/s | 0.16–0.2M | **够**（即 0.2M 帽内的稳态形态） |
| B 事件触发补帧 | 波次/暂停等离散点，≈A 或更低 | ≤0.2M | **够** |
| C 帧间差分 | 估 1–3KB/s/人（差分率 10–30% 为**估**） | 0.5–1.5M | **两可**：差分率与典型帧尺寸实测前不能承诺 |
| D 语义状态同步 | 全量 2–3KB + 增量 50–200B/s → 0.3–0.5KB/s | 0.12–0.2M | 带宽**够**；代价=新开状态导出面+协议维护（§五-4 矛盾仍在） |
| E 观战端事件重放模拟 | ≈D | ≈D | 带宽够也**不可行**：撞「不建第二个 Board/不推算生成伤害」红线 + 跨端确定性无基础 |
| F 中继录制/检查点 | 单次下载 50–200KB 突发 + 小增量 | 50 人首次 = 2.5–10MB 突发 ≈ 7–27s 独占全管道 | 突发是杀手；可 pacing 但 2G 内存机变有状态，架构代价高 |
| G P2P 直连 | 中继 0 | 0 | 官方 300 人部署**不适用**（全 relay），仅自建局域网入口 |
| H 分级：战况条（wave/total 文字） | 几十 B/s | ~20kbps | **几乎免费**，等待席默认档的带宽最优解 |
| H 分级：v1 简图档 | ≤256B×实际频率（若 10ms 节拍 7 周期≈14帧/s → 3.6KB/s，**须实测核对**） | 核对后 0.05–1.4M | 须先核对真实发送频率，必要时降频；核对前不承诺 |
| I 每观看者令牌桶 | 不减总量 | 不减 | 正交项：解决「挤掉谁」，不解决「装不装得下」 |
| J 观战端本地录像 | 中继 0 | 0 | 正交项，随时可做 |

### 8.3 在此约束下成立的组合形态（机械算术，非推荐）

- 0.2M 帽 = 每台 25 人 × 4KB/s ≈ **「每人每 20 秒一张 10KB 快照，其间本地推演」**——A/B + 单次快照批正好落在这条算术线上。
- 想把 50 人都放到「流畅连续画面」，3M 两台机给出的余量只够典型帧 ≤4KB@1fps——这要么靠 C 差分把帧压进 4KB（未实测），要么靠 D 把画面换成语义重建（协议面贵）。
- 等待席/默认档用 H 战况条（~免费），完整画面按需升级并排队——是唯一能把「50 观战」和「0.8M 余量」同时装下且不动红线的组合。
- 单机坏情况（50 观战全在一台）：所有余量减半，上述每个「够」都要再除以 2。

### 8.4 一次便宜测量可消掉的最大不确定度

对局内记录一局真实观战帧的**编码后尺寸分布**（轻/重草坪、五地形），以及 v1 简图档的实际发送频率——两个数落定后，上表「现行连续流够撑几人」「C 差分是否可行」「简图档要不要降频」三条全部从「估」变「实」。

## 九、建议可行方案与 P2P 打洞评估（2026-10-25 追加，待用户批准后实施）

### 9.1 第一期：分级观战（与在实施的单次快照批同向，只补参数与小件）

1. **主体验 = 单次快照 + 本地只读推演**（本批进行中：显式视觉态/动画采集、一次请求、全局限额）。
2. 参数定案建议（§8.3 算术自洽）：请求冷却 **5s**；全局合计帽 **0.2Mbps**；中继显式配置 `SendBudgetMbps≈0.2`；`observerMemoryLimit` 8MB→**1MB**。超帽请求排队或回 BUSY 提示，不挤战斗。
3. **补帧（第二个小批）**：源端在波次推进/暂停恢复时主动补拍（B 事件触发，帧头 wave/total/flags 字段已备）；可选叠加 20–30s 兜底定期。
4. **等待席默认战况条**（wave/total 文字，≈免费），完整画面按需升级；冻结信息加「快照已 N 秒」角标。
5. 验证：既有六席五观众/重连等待席回归 + 一局真实帧尺寸实测（§8.4）。

### 9.2 第二期（可选，独立批次）：P2P 观战直通道

- **线路阶梯**（借 Isaac-Link 的多线路自动选路模式，不借 Steam）：局域网 DIRECT（已有）→ IPv6 直连（国内家宽/4G5G 普及率高，有公网 v6 即免打洞）→ IPv4 UDP 打洞（中继当介绍人，它已知双方公端点）→ **失败自动回落中继，保底不劣化**。
- **与观战流的契合**：快照幂等、最新帧优先、序号+CRC 已有，天然容忍丢包——不需要为 UDP 重造可靠层。
- **前提工作**：`NetLink` 现为纯 TCP（双端 `SOCK_STREAM` 实证），须新增 UDP 通道；Go 中继加打洞协调与路径选择；真机/混合跨网验证。
- **收益**：打洞成功的观战对中继出口归零（50 观战全成功=省 0.2M；人数继续涨时价值放大）。**对局本体流量不动**，仍走已验收 relay。
- **风险**：手机 CGNAT/对称 NAT 打洞成功率要实测（国内移动网络比例高）；P2P 暴露对端 IP（观战场景风险小，但需在玩家口径里明示）；新传输层继承双端验证债。

### 9.3 P2P 打洞原理速记（名词解释用）

NAT 把内网 ip:port 映射成公网 ip:port；「打洞」= 双方**几乎同时**向对方公端点发包，让各自 NAT 先建好映射，后到包即可穿透。可打洞程度由 NAT 类型决定：锥形（全锥/受限/端口受限）可打，**对称 NAT 与运营商级 CGNAT 基本打不通**。STUN=问公网服务器「我的公端点是什么」；TURN/中继=打洞失败后由服务器转发兜底；IPv6 有公网地址则无需打洞直连。TCP 打洞远难于 UDP（需同时打开+NAT 配合）。
