## 一、现状（方案基于的已确认事实）

- 三选一屏每次从「8 条全局增益 + 单株升级」混池抽 3 条互不重复；单株的**只对卡池里已拥有**的植物出
  （`RunState::RollChoices`，RunState.cpp:178-197）。全局 8 条是保底，池子恒 ≥ 8。
- 单株升级原为 **5 条**（批 14 后 48 条满编，见 §六），落点都已实现：

| 现有单株 | 效果 | 落点 |
|---|---|---|
| 豌豆射手 Pea Volley | 每次多发 1 颗 | Plant.cpp:4788（多发循环，按 `mSeedType` 取数——直射系免费） |

- 叠加：`BuffStack{id, 层数}`（RunState.h:72），**现在一律无限叠**（同名跨屏再来 = +1 层）。
- id 空间：`id < 8` 是全局；`id − 8` = 单株表下标。检查点只存 `{id, 层数}`，不存类别。
- 数值取用：`RunBuffMul / RunBuffAdd / RunPlantUpgradeMul / RunPlantUpgradeCount`
  （LawnApp.cpp:1814-1848）。乘数公式 `1 + 每层 × 层数`（线性；乘算条目的叠法见 §2.3），
  `RunBuffMul` 内部夹下限 0.1。非闯关局自动中性值，落点不需要判 `mRunState`。
- 检查点（`userdata/run%d.dat` v3）里 buff 段 = `u16 条数 + 每条 (u16 id, u16 层数)`，
  读档保护 `条数 > 64` 拒收。

## 二、机制改动（四件；不动协议、不动检查点格式、不动 MOD_BUILD）

### 2.1 单株表 5 → 48 条（按 SeedType 顺序）

- 新表按 SeedType `0..47` 排（每株一条，共 48 条）。**前 5 条天然留在原位**——现有 5 株恰好就是
  SeedType 0..4——所以老检查点里的单株 id 不用迁移。48 条齐了还有个顺手的性质：
  表下标 == SeedType（单株 id = `8 + SeedType`）。
- 模仿者（SEED_IMITATER = 48）**不做**：它不进卡池、不进候选（要先指定模仿对象），
  表里也不留占位条目。
- 现有 5 条效果保留（只补上限值）。新增 43 条的效果、数值、上限见 §四。
- 无人按名引用现有 `RUN_UPGRADE_*` 枚举常量（只在枚举里躺着）——新增 43 条**不必**补枚举名，
  表本身够用；想对称也可以补。

### 2.2 新增「层数上限」（两张表都加 `mMaxStacks`，0 = 无限）

- 字段加在 `RunBuffDef` / `RunPlantUpgradeDef` 的**末尾**：旧初始化不填自动是 0（无限），
  要封顶才填数。
- 抽取过滤（`RollChoices` 增益分支）：`GetBuffCount(id) >= 上限` 的条目不进候选
  ——**到顶就抽不中你**，而不是"抽得到但没效果"。
- 已超上限的旧档（老检查点里的层数可能超过新上限）：**保留层数、不追溯削减**，
  只是不再抽到。理由：削旧档要动读档逻辑，收益只是数字好看，不值。
- 全局 8 条也可以封顶，建议值见 §三（你可以全部留 0 = 无限）。

### 2.3 叠乘模式（条目可选「线性 / 乘算」）

- 用户定案（2026-10-03）：全局「急袭」改**乘算**——每层在已有结果上再乘一个系数
  （n 层 = `(1+每层)^n` 几何叠乘），而不是现在的 `1 + 每层 × n` 线性。
- 实现：两张表的条目加一个模式标记，`RunBuffMul` 里按模式分派；下限 0.1 的夹取不变。
- 检查点不受影响（只存层数，不存模式）。

### 2.4 候选不足三条的守卫（纯防御）

**定案（Q5，2026-10-03）**：不会真缺——无限条目（全局 火力/扎根/急袭/速种/储备/爆破 +
单株 豌豆/樱桃/坚果/土豆雷）不封顶、可以一直叠，池子恒 ≥ 3 条。代码仍按防御写：

- 过滤后不足三条 → 缺的格子填哨兵 `0xFFFF`，选择函数与屏上按钮对哨兵直接忽略
  （**空着不画、不可点**）。
- 一条都不剩 → 这次欠的增益屏直接作废（`mPendingBuffPicks = 0`）。
- 保留守卫的理由：空池时 `MTRand::Next(0)` 是 `% 0` 整数除零（MTRand.cpp:168-171）——直接崩。

### 2.5 文案与层数显示（定案 Q6：两样都做）

- 封顶条目的说明文案追加「，至多 N 层」（实现为**取文案时**按 `mMaxStacks` 机械追加，
  见 `RunBuffs.cpp` 的 `GetRunChoiceDesc`——基础文案不手写这句；本文 §四的说明列是**不含**
  它的基础文案）。
- 三选一屏画「已有 x/N」（`RunPickDialog` 现在只画名字+说明）。
- **单株升级列顶画一行【植物名】**（2026-10-03 玩家反馈补，非批次）：按钮名字是英文位图
  字体、说明文案批 2 起多数不含植物名（「射击间隔逐层 ×0.75」这种），屏上分不清是哪株的
  ——`RunBuffs.cpp` 的 `GetRunChoicePlantName`（SeedType→中文名，全局增益返回 NULL）+
  `RunPickDialog` 画标题行；列高改按「描述行数 + 标题行 + 已有行」推。

### 2.6 不改什么

- **检查点格式不动**：上限在静态表里、不进档；id 空间不变；日后满编 56 个 id ≤ 读档保护 64。
- **联机协议不动、MOD_BUILD 不动**：这套系统纯本地——候选、选择、效果都只影响本机棋盘，
  联机里"选什么各选各的"本来就是设计（docs/04 §一「闯关（R5）」）。不上线、不抬代次。
- 非闯关局不受影响（取用口自动中性）。

### 2.7 通用挂点语义闸门（修正批，2026-10-03）

四处通用挂点（血量 `Plant.cpp:484`、射速节奏 `Plant.cpp:976`、多发循环 `Fire`、
种植冷却 `SeedPacket.cpp:885`）此前对**表里任意条目**消费 `mul`/`count`——语义无关的条目
会静默生效：有血量乘数的条目每层缩双发血量 25%（`-0.25` 被当血量乘数用）、寒冰行把雪豆
射速拉长、玉米投手够到多发循环就多发玉米、睡莲行把睡莲种植冷却 ×3。批 1..9 靠"条目恰好
只够到一个口"侥幸没出大事，批 10 投手族同时够到多个口，先修。

改动：`RunPlantUpgradeDef` 加 `mKind` 字段（`RunPlantUpgradeKind` 枚举：EFFECT=0 /
HEALTH=1 / RHYTHM=2 / SHOTCOUNT=3 / COOLDOWN=4），四个通用挂点改走
`LawnApp::RunPlantUpgradeMulKind/CountKind`——**Kind 不符 = 中性值（乘 1.0 / 加 0）**，
只有标签相符的条目被该挂点消费；未打标（EFFECT）的条目只对它自己的专门挂点生效。
14 行打标：血量 6（坚果墙/高坚果/睡莲/南瓜头/花盆/保护伞）、节奏 4（双发/杨桃/卷心菜/
机枪）、多发 2（豌豆/三线）、冷却 2（火爆辣椒/海蘑菇）。专门挂点（磁力菇充能、雪豆减速、
樱桃/毁灭菇/土豆雷半径、地刺减速、地刺王循环、寒冰菇冻结、窝瓜眩晕、产出三循环）继续走
不带 Kind 的通用口——它们按挂点自身语义找行，天然不会误伤。

取证（自测日志 [t10a]）：30 行 kind 分布全对；双发 3 层 RHYTHM=422‰ 而 HEALTH=1000‰
（中性——修前会被缩成 250‰）；寒冰三列 1000/1000/raw 1900‰；睡莲 3000‰；辣椒
COOLDOWN=422‰；豌豆 shot=2 而 rhythm/cooldown 均 0；坚果 2000‰。
